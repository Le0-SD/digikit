# blk93@0x1c4f81 — likely a windowed-sinc / polyphase sample-rate converter, not a 2-tap oscillator

- **Bounds**: entry `0x1c4f81`, exit `0x1c5334`, matches `tools/sharcinv.py`'s
  inventory exactly (`entry=1855361 exit=1856308 n_insns=375`). Cross-checked
  against `tools/sharcflow.py`'s return list: the return that opens this span
  is at `sw=0x1c4f7c` (`after=0x1c4f81`); nothing else closes earlier. **[V]**
  Caveat: `sharcinv.py` marks `tail_split_into: blk93@0x1c5334` — `0x1c5334`
  is itself a call target from elsewhere, so it opens a new function there
  per the tool's own convention; confirmed by decoding a few instructions
  past `0x1c5334`, which is a block of `15b` register-saves to `DM(I6+...)`,
  i.e. a genuine new prologue, not a mid-loop artifact. **[V]**
  Second caveat, more important: this function's own body does **not**
  return through `0x1c5334`. Its one unconditional exit
  (`0x1c5264`, `cond=31 JUMP rel -782`) jumps **backward** to `sw=0x1c4f56`,
  landing inside the *previous* return-delimited span (`0x1c4ecf`–`0x1c4f7c`,
  the routine that precedes this one) at a point partway through a ~20-register
  restore sequence (`I0-I3,I5,I12`, `M1-M3`, `B3`, `R3,R5,R6,R7,R9-R11,R13-R15`
  loaded from `DM(I6+102..124)` via `15b`), which falls into that routine's own
  `9b_abs` return at `0x1c4f7c` and its `25c_rframe` delay slot at `0x1c4f80`.
  So `0x1c4f81`'s only exit is a **shared restore+return epilogue physically
  inside a different, sharcinv-classified function** — the reverse of the
  documented "callee inside caller's span" case (module docstring in
  `sharcinv.py`); here a callee-less **jump** reaches backward across a
  return boundary into someone else's epilogue. `n_insns=375` therefore
  undercounts what this call actually executes on its one live path by the
  size of that shared epilogue. **[V]**

- **Callers**: inventory says 0; a byte-level scan of `blk93`'s payload for
  Type 8a `CALL` (`b=1`) instructions whose relative target resolves to
  `0x1c4f81` found none, but that scan is **not** alignment-safe (SHARC+
  instructions are 2/4/6 bytes; scanning every even offset produces false
  positives elsewhere, e.g. 391 raw `b=1` hits in blk93 against the ~51 real
  ones `blk93-1cb4b2.md` established with a properly aligned walk). No
  positive caller evidence, but this is **[O]**, not a settled leaf-caller
  claim — a same-block Type 8a call is the only way a caller could be
  invisible to `sharcinv.py`, and that hasn't been ruled out rigorously here.
  **Callees**: **two**, both invisible to `sharcinv.py`/`sharcflow.py`
  (Type 8a `CALL`, per the repo-wide method gap): `0x1c06ba` (the shared
  reciprocal — `blk93-1cb4b2.md` established 50/51 of blk93's Type 8a calls
  target it), called twice, at `0x1c5193` and `0x1c51f8`, both
  `cond=31` (unconditional) with `b=1 a=0 j=1 ci=0`. Plus the one callee
  `sharcinv.py` **does** see (`25a_direct`, absolute): `blk69@0xb80000`, at
  `0x1c525d`. **[V]** (all three decoded directly from the instruction
  stream).

- **Label**: inventory label *interpolating table lookup / wavetable
  oscillator*, confidence 0.4 (the lower of the two confidence tiers the
  labeler uses for this shape — it fired on `external_hits >= 2` rather than
  a genuinely named table). **The `external_0x80xxxxxx` literal hits that
  triggered the label are a false positive**: all three are the bit pattern
  `0x80000000` loaded three times at `0x1c4f8b`/`0x1c4fbf`/`0x1c4fc5`
  (`R0`/`R6`/`R3 = -0.0`, used as comparison sentinels, not addresses) —
  `classify_literal()` buckets any 32-bit literal whose top byte is `0x80`
  into `external_0x80xxxxxx` regardless of whether it's an address or just a
  negative-zero float immediate. **[V]** (matches the function vector's
  `float_immediates` list exactly: three entries with `bits=0x80000000`,
  `float=-0.0`, and `literal_regions.external_0x80xxxxxx=3` — a 1:1 match).
  So the label's own stated reason doesn't hold up. It is nonetheless
  **directionally right for a different reason the labeler didn't see**: see
  below.

## What it computes

Refutes the specific idiom the label predicts (a simple `trunc`/`+1`/two-tap
linear blend), but the broader family membership holds up: this reads as a
**short-kernel (6-tap) MAC-based interpolating resampler with a fixed-point
phase accumulator**, i.e. the same family as the wavetable engine's stage 5/6
(`0x1cc79e`/`0x1cbf07`, documented in `docs/findings/06-sharc-engine-and-startup.md`),
just built from a convolution sum instead of a plain 2-tap blend. **[D]** —
read once, not cross-checked by a second agent.

Evidence, in order:

1. **A 64-bit-style fixed-point phase accumulator.** Two working registers
   `R4`/`R13` are advanced every loop iteration by add-with-carry:
   `R4 = R10 + R4` then `R13 = R11 + R13 + ci` (seen at `0x1c50f5`/`0x1c50f8`
   inside the first 64-count loop, and again at `0x1c5304`/`0x1c5306` and
   `0x1c531c`/`0x1c531f` in the branch-dispatch code around the second). The
   step pair `R10`/`R11` is built once, early, from two raw words loaded from
   the caller's context (`R6 = DM(I4+98)` at `0x1c4f94`, `R11 = DM(I4+99)` at
   `0x1c4f91`) via `lshift by 31` and `rot by 1`/`rot by 255` (`0x1c4f97`,
   `0x1c4f9d`, `0x1c4fa3`) — sign/mantissa-style bit surgery on a
   caller-supplied rate/step value, not a literal constant. **[V]** for the
   mechanism; **[O]** for exactly what the two source words at `I4+98/99`
   represent (pitch/playback-rate is the natural read given everything else
   here, not independently confirmed).

2. **The shared reciprocal, called with the documented `2^32` correction.**
   Both calls to `0x1c06ba` are immediately preceded by `R1 = 0x4f800000`
   (`= 2.0^32`, the exact constant `docs/findings/06-sharc-engine-and-startup.md`
   names for stage 5's "unsigned 32-bit phase to float" idiom) and immediately
   followed, in the branch-delay slot, by `F8 = F8 + F1` — i.e. `float(R2)`
   was computed just before the call (`0x1c51f2`: `compute:F8 = float R2`),
   and the delay-slot add undoes the sign error `float` introduces when `R2`'s
   top bit is set, giving a correct unsigned-to-float conversion before
   the reciprocal is taken. Textually identical to `0x1cc79e`'s "reciprocal
   helper for step size". **[V]**.

3. **Two structurally identical 64-count integer hardware loops**
   (`12a_imm`, literal trip count `64` both times — matches the inventory's
   `loop_literal_values: [64, 64]` exactly), at `0x1c5096` (body
   `0x1c5099`–`0x1c5100`, length field `107`) and `0x1c52ab` (body
   `0x1c52ae`–`0x1c5327`, length field `125`). **[V]**. Per iteration, each
   loop:
   - advances the phase accumulator (item 1);
   - derives a window pointer `I5` (first loop) or `I1` (second loop) as a
     **fixed literal base plus a runtime-computed, phase-derived offset**:
     `I5 = 0x0025d940` (`0x1c50aa`, loaded as a raw 32-bit literal, decoded
     by the disassembler as a float bit pattern but used purely as an
     address) then `I5 = I5 + M2*scale` (`7a` modify, `0x1c50b6`), where `M2`
     was itself just set from a `lshift`/`rot` of the phase-step register
     (`0x1c50a6`/`0x1c50a9`/`0x1c50ad`) — i.e. **the fractional part of the
     phase selects which window of the buffer to read**, the textbook
     "polyphase index" move. The second loop does the identical sequence
     through `I1` instead of `I5` (`0x1c52bf` loads the same literal
     `0x0025d940` again). **[V]** for the addressing mechanism.
   - reads **three consecutive long-word (8-byte) entries** from that window,
     `DM(I5+0)`, `DM(I5+2)`, `DM(I5+4)` (word offsets, `15b ... [load long]`
     — 2-word/8-byte stride, so three back-to-back paired entries), and MACs
     them against **six** taps of a second array walked *sequentially* via
     `I4`/`M5`/`M6` post-modify (no phase jump — a plain linear walk), one
     `mrf = acc + Rx*Ry (SSF)` per tap (`0x1c50bb` through `0x1c50dd`, six
     multiply-accumulates total, matching the inventory's `mac: 10` combined
     across both copies plus a couple of one-off MACs elsewhere). The
     accumulator is saturated (`R2 = sat mrf/mrb MOD2`), converted to float
     (`F2 = float R2 by R6`/`by R9`), and stored once per iteration
     (`DM(I2 pre-mod M6) = R2`). **[V]** for the whole per-iteration shape;
     **[O]** for whether the 6-tap array is coefficients-with-history or the
     reverse (see Memory below — both pointers are runtime-only, so the
     static image can't say which side holds the fixed kernel).
   This is a **6-tap MAC per output sample, batch-producing 64 samples per
   call, run twice** (through `I5`/`R6` and `I1`/`R9` respectively) — not the
   single 2-tap blend the label's idiom describes. **[V]** for the shape,
   **[D]** for the "SRC" naming (plausible, not confirmed against ground
   truth).

4. **A register-count float loop in between** (`12a_ureg`, `LCNTR=R0`, body
   `0x1c5147`–`0x1c516a`, 39 sw — inventory's `loop_register` entries include
   this) guarded by three comparisons of `F12 = abs(F0)` against `F1`
   (`0x3a83126f` = `0.001`, loaded at `0x1c513f`), `F0`, and `F2`
   (`0x1c5148`–`0x1c5162`), selecting one of three onward branches. Reads as
   a magnitude-threshold guard picking among near-zero / mid-range / other
   handling before the phase-accumulator loops run — **[O]**, not traced to
   a specific named idiom (not the `x <- x*(2-|x|)` envelope shape documented
   for `0x1cb3d8`; no repeated self-multiply seen). Two further small
   register-count loops (`LCNTR=R8`, body 12 sw, at `0x1c51ca` and
   `0x1c522e`, both `mode=1`) do a short `F1=F1*F12; F1=F2+F0` /
   `F2=F2*F12; F2=F1+F0` alternating chain — a short Horner-style
   accumulation, **[O]** for what polynomial.

5. **The branch/dispatch region is not fully traced.** Roughly 15 conditional
   `8a_rel` branches connect several small shared sub-blocks that repeatedly
   re-read caller-context fields at dynamically-computed offsets (`M4`/`M3`
   set to literals `380`–`444` then used as the modifier in
   `DM(I4 post-mod M4)`, i.e. `I4+380` .. `I4+444` in effect) and take a
   `leftz` (count-leading-zeros) of each before branching — validation or
   dispatch on small integer fields, not decoded further. **[O]**.

## Structure

- **`0x1c4f81`–`0x1c4ff6`** (prologue, ~28 insns): loads 8 words from the
  caller's `I4` at word offsets `98,99,100,101,104,105,106,107` (`15a`,
  pre-modify-no-writeback form — *not* the literal absolute addresses the
  raw field printer suggests; see Memory), builds the phase-step pair
  `R10`/`R11` from two of them by bit rotation (item 1 above), and does
  three `compu` (unsigned compare) checks against a repeated constant `70`.
  Falls to one of two short continuations depending on `cond=1` at
  `0x1c4ff6`, both landing at `0x1c5016`.
- **`0x1c4ff9`–`0x1c5030`**: two dynamically-indexed field reads
  (`M4=443`/`444` then `DM(I4 post-mod M4)`, i.e. `I4+443`/`I4+444`),
  each followed by `leftz`; a `BIT-TEST USTAT1+8` (`18a`, mask
  `0x23e7808`, mode-flag test — not decoded further, **[O]**); one
  instruction (`0x1c5030`) decodes as `Type10a_rel` (SHARC classic PGR
  "with PC-relative jump", `out/refs/adsp-2136x_2137x_214xx_pgr_rev2.4/pages/p0458.txt`)
  — a fused compute+`DM(I,M)`-transfer+conditional-jump form **not present in
  `tools/sharc_visa_tables.py`** (confirmed: exact 48-bit match against
  `tools/sharcspec/decode_table.json`'s `Type10a_rel`, zero against every VISA
  form). Its own `reladdr=0`, so on this occurrence it always falls through;
  decoded here as `R3 = DM(I0,M4) ; compu(R2,R0)`. **[V]** the decode,
  worth adding to `tools/sharc_disasm.py`'s table as a known (rare) gap
  alongside the documented `0x1e`/`0x1f`/`0xd9`/`0xda` ones.
- **`0x1c5033`–`0x1c504a`**: two more dynamically-indexed reads (offsets
  `443`, `444` again) each gated by `leftz`+branch, converging on
  `0x1c504a`.
- **`0x1c504a`–`0x1c5096`**: `I0 = I4 + 440` (**byte** offset — this is the
  unscaled `19a` "raw-byte modify" form, not `19a_scaled`, so `440` is bytes,
  ≈ word `110`, i.e. right after the 12-word scalar block the prologue reads
  at `I4+98..109`: consistent with an array starting immediately after that
  block); `I13 = I4` (saves the incoming context pointer — everything from
  here on rebuilds `I4`/`I5`/`I2`/`I1` from `I13`, not from the original
  argument register); a burst of `15b` loads/stores shuffling small
  negative offsets off `I4`/`I5`/`I2`/`I1`/`I6` (`-2,-3,-4,-5,-6,-9,-10`
  words); one conditional branch (`0x1c507f`, `cond=23`) that either falls
  into the first 64-count loop's setup or jumps ahead to the second
  loop's setup at `0x1c529b`, skipping the first pass.
- **`0x1c5082`–`0x1c5101`**: first 64-count hardware loop and its setup
  (item 3); ends at the loop-cleanup instruction `21a` (`0x1c5101`,
  undecoded — SHARC's post-loop MR-saturate housekeeping form, **[O]**).
- **`0x1c5104`–`0x1c526a`**: a second, larger dispatch region — more
  dynamically-indexed field reads (offsets `380`–`382`, `436`, `441`),
  the register-count float-threshold loop and the two 12-sw MAC loops
  (item 4), the two calls to `0x1c06ba` (item 2), a direct call
  `0x1c525d: JUMP/CALL abs 0xb80000` (to blk69), and the loop-exit sequence
  ending in the unconditional backward jump to the shared epilogue at
  `0x1c4f56` (Bounds, above). This region has several internal backward
  branches (e.g. `0x1c5271`, `0x1c5274`) reusing the same sub-blocks from
  multiple entry points — not fully traced. **[O]**.
- **`0x1c526b`–`0x1c5334`**: reached only when `0x1c507f`'s branch is taken
  (skips the first pass). Rebuilds the same context aliases and runs the
  second 64-count loop (item 3, via `I1`); falls into the same unconditional
  exit at the end (mirrors the first pass's tail).

No `RFRAME`/frame-push is visible at entry; `I6` (used throughout as a
LIFO scratch pointer, always stepped by a fixed `-5`/`-6`/`-7`/`-2`/`-3`/`-4`)
is inherited live from the caller, consistent with every other function
read in this block so far.

## Memory

- **`I4 + {98,99,100,101,104,105,106,107,108,109}`** (word offsets, `15a`
  form — address is `I<i> + addr`, *not* the literal `addr` field; the raw
  disassembler fields print `addr[15:0]` alone and are easy to misread as an
  absolute address, as an earlier scratchpad script for `0x1c18a6` did).
  `sharc_trace.py`'s own model agrees (`--summary` run: `"I4 + 100"`,
  `"I4 + 101"`, etc.). If the caller's `I4` is the parameter-frame base
  itself (`FRAME_LO = 0x2558DC` in `tools/sharcinv.py`), these land at byte
  offsets `0x255a54`–`0x255a94` — well inside the documented frame
  (`0x2558DC`–`0x2560DE`). **[O]**: `I4`'s concrete value is never set inside
  this function (it's a pure incoming argument), so this can't be confirmed
  statically, but the offset arithmetic is consistent with **this being the
  still-unidentified "SRC page" consumer** task item 7 asks about — the
  phase-accumulator/reciprocal/interpolating-kernel shape found here is
  exactly what a sample-rate-conversion parameter block would drive. Worth a
  caller trace (which function sets `I4` before calling in, and does its
  own frame math corroborate `FRAME_LO`+word-offset-98?) to settle.
- **`I4 + {380,381,382,441,443,444}`** (word offsets, via dynamically-loaded
  `M3`/`M4` + `3b` post-modify — these scale like the prologue's `I4+98..109`
  reads, per-repo convention M-indexed ×4 under the 32-bit-normal-word
  assumption, so in bytes this is `I4+1520`..`+1776`, still inside the
  documented `FRAME_LO`–`FRAME_HI` span if `I4==FRAME_LO`) — read in the
  branch-dispatch region, always followed by `leftz`. Same frame-relative
  caveat as above; not narrowed further. Distinct from the next two entries
  (`436`/`440`), which are **raw byte** offsets from a different addressing
  form (`19a`, not `3b`/M-indexed).
- **`0x0025D940`** — **a previously-uncatalogued address**, not in any of
  the named tables (`tools/sharcinv.py`'s `NAMED_TABLES`: cosine pair
  `0x8055C440`/`0x8055C640`, float pair `0x8055C890`/`0x8055D890`, exp table
  `0x8045A6C8`, 32-float table `0x8045C3C0`, `0x26BB68`). **Not covered by
  any loaded block** (`tools/sharcldr.py --addr 0x25d940 --addr-space byte`
  → "not covered by any loaded block"), i.e. RAM, populated only at runtime
  — the same situation `blk93-1c14e7.md` found for its 32-entry pointer
  table: the static image cannot show its contents. **[V]** for the address
  and its ROM-coverage status; **[O]** for what it holds. Access pattern:
  base `0x0025D940` (loaded as a raw literal twice, identically, at
  `0x1c50aa` and `0x1c52bf`), indexed by `base + (phase-derived M-register
  offset)`, read three 8-byte long-word entries per access (`+0`,`+2`,`+4`
  words = 3 consecutive pair-entries). Apparent entry size 8 bytes; total
  entry count and exact index stride are runtime-determined (the `M2`
  scale factor comes from a hardware DAG M-register, not a static
  constant) — **[O]**. Given the phase-selected-window-of-a-fixed-buffer
  shape (item 3 above), the most consistent naming is a **polyphase
  interpolation kernel bank** (one sub-filter per phase bin), shared
  across whatever calls through here (same literal address both passes,
  unlike the per-call-relative `I4+440` array) — **[D]**, not confirmed.
- **`I4 + 440` (bytes, ≈ word `110`) / `I5 + 436` (bytes, ≈ word `109`)** —
  built by the unscaled `19a` "raw-byte modify" form at `0x1c504c`/`0x1c5243`,
  landing right after the 12-word scalar block (`I4+98..109`) the prologue
  reads. This is the array walked *sequentially* by the 64-count loops'
  inner MAC chain (`I4`/`M5`/`M6` post/pre-modify, no phase jump).
  Caller-relative, so its absolute address varies per call — same situation
  as `0x1c14e7`'s per-track buffers (not visible in the ROM image either
  way, since it's relative arithmetic on an unknown `I4`). **[O]**.
- **None** of the task's other named tables (cosine, exp829, table32, the
  128-float pair `0x256388`/`0x256588`, the audio rings `0x262138`/
  `0x262938`/`0x263138`/`0x263938`) are touched anywhere in this function.
  **[V]** (full instruction-by-instruction pass, no literal in any of
  those ranges).

## Interface

- **`I4` in** is the only externally-meaningful register at entry — every
  read in the prologue is `DM(I4 + word_offset)`, and `R4`/`R8`/`R12` are
  all overwritten before their first use (`R12` from a `17b` immediate at
  `0x1c4f84`, `R8` from `DM(I4+104)` at `0x1c4f88`, `R4` from `DM(I4+101)`
  at `0x1c4fb4`) rather than read as incoming arguments. **[V]**.
- `I4` is saved once, early, into `I13` (`0x1c504f`) and again into `I12`
  (`0x1c5018`/`0x1c5022` area — both are used later as the stable anchor to
  rebuild `I4`/`I5`/`I2`/`I1` for the two passes), so the function does treat
  its one incoming pointer as precious, consistent with a per-call context
  argument rather than scratch. **[V]**.
- **Nothing is visibly written back to a caller-owned location** apart from
  the two `DM(I2 pre-mod M6) = R2` stores inside the 64-count loops — and
  `I2` is itself derived from `I13`/`I12` (the incoming `I4`), so those 64
  (×2) samples per call land in a caller-relative buffer, not a hard-coded
  global. Whether that's the same struct the caller reads back afterward,
  or a separate output ring, is **[O]**.
- `I6` (LIFO scratch) and `M5`/`M6`/`M7` (used throughout for post/pre-modify
  stepping) are inherited live from the caller and never (re)initialized
  here — same convention as every other function read in blk93 so far.

## Open

- The ~15-branch dispatch region (`0x1c5033`–`0x1c526b`) is not fully
  traced; several of its sub-blocks are reached from more than one branch
  and share code, which needs a proper CFG rather than linear reading to
  pin down.
- What `I4+98`/`I4+99` (the phase-step source) and `I4+380..444`
  (the dispatch fields) actually name — settling whether `I4` is exactly
  `FRAME_LO` (making this the SRC page's consumer) needs a trace of this
  function's caller(s), which the Type 8a gap currently hides.
- Whether `0x0025D940` is a shared polyphase kernel bank or a shared
  history/delay buffer (both fit the access pattern; only a live capture
  would show the actual floats, and the task rules out running the
  emulator here).
- `Type10a_rel` at `0x1c5030` and the `21a`/`21c`/`20a` instructions
  (`0x1c5101`, `0x1c526a`, `0x1c5280`, `0x1c5165`, `0x1c5168`, `0x1c5328`)
  are decoded from field layout only (classic PGR tables, not VISA-confirmed
  and not modelled by `tools/sharc_trace.py`) — worth confirming against a
  second independent reading before relying on their exact semantics.
- Two `2c` short-compute opcodes seen (`0x1c517a`-ish region: `R8 = R8 ?a
  R2`, `R2 = R2 ?8 R0`, `R12 = R12 ?b R2`) use opcode values (`0xa`, `0x8`,
  `0xb`) not in the short-compute name table used here (`decode_short_compute`
  only names `0,1,2,3,4,5,6,7,C,D,E`) — minor tooling gap, left unresolved.
