# Digi emulator handover — 2026-09-13

Supersedes nothing in `HANDOVER-2026-09-12.md` except its work-item 1, which

## The front panel works

You can press buttons and turn encoders on both builds, and the firmware
responds. That was work item 1 and it is finished.

`emu/panelin.py`:

```python
press(m, profile, channel, bit, held=0)
release(m, profile, channel, bit, held=0)
buttons(m, profile, channel, mask)      # whole 8-button group state
encoder(m, profile, channel, delta)     # signed detents
state(m, profile)
```

Verified on Digitone: `encoder(m, profile, 0, +1)` replaces the on-screen
`TUN1` label with its live value `0.00`, and pressing channel 0 bits 0..5
selects the TRIG / SYN / FLTR / AMP / FX / LFO pages -- the real page-button
row, in physical order.

## The panel is not memory-mapped

This is the thing that cost the most to establish, so do not re-derive it.
`tools/mmiotrace.py` (new) profiles MMIO by *recurrence* rather than total,
chopping a run into fixed instruction-count windows so a scan loop is
distinguishable from an init burst. Over 60M post-intro instructions on each
build it finds **zero GPIO, zero DSPI, zero unclaimed addresses** -- only
timers and the UART8 transmit DMA. Nothing scans a key matrix.

Also ruled out: all six FlexBus chip-selects read zero, and the only non-RAM
regions ever mapped are `0x80000000` (boot ROM) and `0x8C000000` (the DSP).
The panel is not on an external bus either.

A separate microcontroller does the scanning and talks over **UART8** at
156250 baud (5x MIDI rate). Events arrive by eDMA channel 34 into a
1024-byte ring, then vector 154.

**UART8 is not MIDI, and not a text console on the wire.** Both claims exist
in older docs and both mislead. MIDI DIN is **UART9** at 31250 baud (verified:
`pea #0x7A12` into the UART9 init), entirely unmodelled. The `#HELLO` console
is real but is a software dispatcher that `emu/serial.py` reaches by injecting
into its queue, bypassing the wire.

## The wire protocol

    header = (tag << 4) | channel

    tag 0x2   1 byte    buttons -- an 8-bit STATE BITMASK for that channel's
                        eight buttons. The firmware XORs against the previous
                        byte and derives edges itself; there is no release
                        message on the wire.
    tag 0x3   1 byte    encoders -- a SIGNED delta. Not gray code, not
                        separate inc/dec messages.
    tag 0x7   8 bytes   a block the console task consumes; not input.

Any other tag is parsed and discarded. No length field, no checksum.

The parser is byte-identical in both builds; only data addresses move. So
`emu/symbols.py` gained five symbols chained off one Fixed anchor:
`uart8_init` is BSP-layer code at the same address in both images, the
`clr.l` operand at +0x18 is the driver's globals base, and the field offsets
inside that block are identical (+0x10 ring, +0x30 consume index, +0x40
receive callback). That is also the fix for `emu/serial.py`, which hardcoded
Digitakt's and on Digitone read `0xFFFFFFFF`.

## Reading events instead of the screen

`tools/panelsweep.py` (new) maps the whole panel by hooking `queue_send` and
decoding the 16-byte event record the firmware itself emits:

    +0x00  type   0 = button, 1 = encoder
    +0x07  control code
    +0x08  encoder value (signed delta)   -- note: union-like layout,
    +0x0B  button flags (0x01 press, 0x10 release)
    +0x0C  timestamp

**Do this instead of diffing the framebuffer.** The record is the firmware's
own output, so it is immune to render timing, modal state and frame tearing.
Framebuffer diffing cost hours and produced two contradictory maps; the
record method mapped all of Digitone in 85 seconds.

`queue_send` (`0x40001896`) is the only literal address the tool uses, and it
is genuinely identical in both builds. Callers and the sink queue are
discovered at runtime by record shape plus a settle-built ignore-set, so the
tool is build-agnostic.

### The maps

Buttons, both builds: `code = channel * 8 + bit + 1` for channels 0..5
(codes 1..48). Channel 6 breaks the pattern in both, and differs between them:

| ch6 bit | Digitone | Digitakt |
|---|---|---|
| 0 | 50 | 50 |
| 1 | 49 | 49 |
| 2 | 0 (unassigned) | 100 *(tentative)* |
| 3 | 0 (unassigned) | 116 *(tentative)* |
| 4..7 | 51, 52, 53, 54 | 100, 101, 112, 111 *(tentative)* |

Digitakt fills the two slots Digitone leaves empty. Digitakt's ch6 bits 2..7
are **tentative**: that build defers some records until the next panel event,
and the reassembly pass is only reliable where a code formula exists to check
against. Bits 0..1 are clean on both.

Encoders, both builds: `code = channel + 1` for channels 0..8 -- eight data
encoders plus level. Signed delta verified at +1, +5 and -1.

Named so far, from screen observation on Digitone: codes 1..6 are the TRIG,
SYN, FLTR, AMP, FX and LFO page buttons; code 24 is SONG; code 53 opens
NOTE EDIT. Everything else has a code but no name.

## Dead ends -- do not repeat these

- **DTCN is not the problem.** The encoder handler reads DTIM0's counter at
  `0xFC07000C`, which reads 0 forever. That is *hardware-faithful*: DTMR0 is
  `0x0000` (stopped, held in reset) at every sample, and nothing in the whole
  image ever writes it. DTCN is a payload timestamp field only -- never a
  gate, divisor or scale. Implementing a free-running DTCN would be inventing
  hardware and would fix nothing.
- **The `< 0x28` debounce gate is not the problem.** It compares a *software*
  tick counter (`0x464b2bb0` on Digitone, incremented by the periodic flush)
  against a per-index stamp array. Measured: 9/9 accepts, 0 discards.
- **Encoders were never broken.** Both dead ends above were chased because
  encoders looked dead. They were not: the observation window was too short
  for the consumer task to be scheduled, so even a known-working *button*
  showed no change in the same run. Read the event record, not the screen.
- **A fixed instruction cap on the intro wait has burned three agents.**
  `sdboot280M.snap` has the intro LIVE at restore; handover fires at ~64-70M
  on Digitone and ~140M on Digitakt. Spin uncapped until the `intro_done`
  hook fires, then settle. Capping it early leaves the timers held and
  silently changes results.
- **MAIN OS loads at `0x40000400`, not `0x40000000`.** Addresses derived from
  a raw section-file offset with the wrong base are 0x400 too low.

## Known limits

- From a settled state, running past ~16-20M instructions raises an
  "INITIALIZING +DRIVE..." dialog that never clears, because the eSDHC model
  does not back bulk block reads. Keep observation windows under that.
- Page buttons behave *momentarily* -- the page reverts shortly after
  release. May be an artifact of `unblock=True` rather than real. Unresolved.
- Digitakt's `boot280M.snap` renders a blank screen post-intro, so screen-based
  identification does not work on that build. The record method does.
