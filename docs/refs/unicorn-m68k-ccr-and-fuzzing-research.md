# Research: Unicorn m68k CCR divergence and deterministic diagnosis

## Summary

There is a directly relevant upstream change already in Unicorn 2.1.4: merged PR [#2161](https://github.com/unicorn-engine/unicorn/pull/2161) made `UC_M68K_REG_SR` reads synthesize CCR bits, but it also sets `env->cc_op = CC_OP_FLAGS` *before* computing them. That is destructive for a lazy `CC_OP_CMP*` state; removing that assignment is therefore a justified local correction, not a missed post-2.1.4 upstream fix. I found no upstream Unicorn issue/PR/commit that covers the remaining continuous-run, code-hook/count-boundary failure, nor a newer upstream QEMU change that adds Unicorn's proposed `update_cc_op()` before `gen_uc_tracecode()`.

The strongest next move is a small, reproducible differential harness around the failing instruction window, comparing one-shot with every partition point and running it under an instrumented Unicorn build. The best independent *semantic* cross-check is a deliberately small Ghidra P-code/SLEIGH or another interpreter test for the exact supported ColdFire subset, while QEMU m68k is best as a closely related, no-Unicorn-hook control—not an independent oracle because Unicorn vendors the same translator lineage.

## Findings

1. **Confirmed: Unicorn 2.1.4 contains the SR-read fix and its destructive lazy-CCR transition.** PR [#2161](https://github.com/unicorn-engine/unicorn/pull/2161), merged 2025-04-13 and included in the [v2.1.3..v2.1.4 comparison](https://github.com/unicorn-engine/unicorn/compare/v2.1.3...v2.1.4), explains that `env->sr` lacks the low five CCR bits and adds `cpu_m68k_get_sr()`. In the current Unicorn source, `reg_read(UC_M68K_REG_SR)` executes `env->cc_op = CC_OP_FLAGS;` then calls `cpu_m68k_get_sr()` ([`unicorn.c`](https://github.com/unicorn-engine/unicorn/blob/7c5db941/qemu/target/m68k/unicorn.c)); the helper computes CCR according to `env->cc_op` ([`helper.c`](https://github.com/unicorn-engine/unicorn/blob/7c5db941/qemu/target/m68k/helper.c)). The explicit `CC_OP` design is lazy: the header says operand/result/type are retained and flags calculated when needed ([`cpu.h`](https://github.com/unicorn-engine/unicorn/blob/7c5db941/qemu/target/m68k/cpu.h)). Consequently, changing the op to `FLAGS` before `cpu_m68k_get_ccr()` discards the selector needed to interpret deferred operands. The reported removal is source-supported.

2. **Confirmed: the existing 2.1.4 regression only verifies a simple post-run SR flag, not hooks, count exits, or continuity.** The upstream Rust regression has `test_sr_contains_flags`, executing a single `moveq` and reading SR after `emu_start`; it has no `UC_HOOK_CODE`, partitioning, `count`, `MOVEM`, `RTE`, or TB-chain coverage ([test](https://github.com/unicorn-engine/unicorn/blob/7c5db941/bindings/rust/unicorn-engine/src/tests/m68k.rs)). A later Java regression commit explicitly says it probably needed updating because of #2161 ([7a89371](https://github.com/unicorn-engine/unicorn/commit/7a89371fd227b89968ad2883475481dfbc1fa908)). This is evidence of narrow coverage, not evidence that the actual CCR calculation is wrong in every case.

3. **Confirmed: the count-boundary/hook theory matches Unicorn's translator structure, but is not an upstream m68k fix.** Unicorn's generic translator stops translating after `db->num_insns >= db->max_insns`, then calls target `tb_stop`; its early `until` path invokes one target `translate_insn` then goes directly to TB end ([`translator.c`](https://github.com/unicorn-engine/unicorn/blob/7c5db941/qemu/accel/tcg/translator.c)). The same file emits Unicorn block callbacks with `gen_uc_tracecode`; target translators emit code hooks pre-instruction. Historic Unicorn discussion explicitly characterizes code callbacks as **before** the instruction and documents exceptional JIT/control-flow behavior ([issue #346](https://github.com/unicorn-engine/unicorn/issues/346)). Thus an exit requested by a hook at N+1 can indeed occur before usual later TB finalization. The suggested `update_cc_op(dc)` immediately before m68k `gen_uc_tracecode()` is a plausible experiment, but I found no upstream Unicorn PR/commit merging it or documenting m68k hook-state synchronization.

4. **Confirmed: upstream QEMU recognizes CC-op synchronization as necessary at TB chaining, but this does not prove the Unicorn hook patch.** Upstream QEMU commit [`7cd7b5c`](https://github.com/qemu/qemu/commit/7cd7b5ca9be805e8a4ced4c07014c24e34812f27) is specifically titled “sync CC_OP before gen_jmp_tb()”. Current QEMU m68k `gen_jmp_tb()` calls `update_cc_op()` only in the single-step/trace exception branch; the direct goto-TB branch writes PC and exits ([`translate.c`](https://github.com/qemu/qemu/blob/3e3ccab1/target/m68k/translate.c)). Its `set_cc_op()` marks the state unsynced, `update_cc_op()` emits `QREG_CC_OP`, and `gen_update_cc_cmp()` stores compare operands and selects `CC_OP_CMP*` ([same source](https://github.com/qemu/qemu/blob/3e3ccab1/target/m68k/translate.c)). This gives concrete rationale to audit every externally visible TB exit, but QEMU upstream has no `gen_uc_tracecode`, so it cannot be cited as having fixed Unicorn’s callback boundary.

5. **Confirmed comparison: current QEMU and Unicorn share the relevant lazy-CCR algorithm; no newer-QEMU code evidence found for a CMP/RTE/MOVEM correction matching this symptom.** Both current QEMU and Unicorn translations contain the same `DisasContext.cc_op`/`cc_op_synced`, `set_cc_op`, `update_cc_op`, CMP flush logic, and `gen_update_cc_cmp` scheme ([QEMU](https://github.com/qemu/qemu/blob/3e3ccab1/target/m68k/translate.c), [Unicorn](https://github.com/unicorn-engine/unicorn/blob/7c5db941/qemu/target/m68k/translate.c)). QEMU's CPU restore callback restores PC and, when not dynamic, `env.cc_op` from TB metadata ([`cpu.c`](https://github.com/qemu/qemu/blob/3e3ccab1/target/m68k/cpu.c)); this is an important breakpoint/restore path to compare with Unicorn. I found neither a later upstream QEMU change touching `RTE`/`MOVEM` that specifically repairs lazy CCR state nor an m68k code-hook mechanism (QEMU does not have Unicorn API hooks). Do not infer a MOVEM/RTE cause merely from their proximity in the firmware trace.

6. **Practical decisive instrumentation is below Python hooks: add translator/runtime probes or use a debug build.** In Unicorn, add a temporary C helper/probe at (a) `set_cc_op`, (b) `update_cc_op`, (c) `gen_update_cc_cmp`, (d) immediately before/after the generated code-hook call, and (e) `cpu_m68k_get_ccr`/`flush_flags`; log PC, `s->cc_op`, `s->cc_op_synced`, and `env->{cc_op,cc_n,cc_v,cc_z,cc_c,cc_x}`. Translator-side logs describe generated code, not the per-execution host-register values; the runtime helper probe is essential. Build unoptimised with symbols (`CFLAGS='-O0 -g3'`, Unicorn’s issue discussion uses `UNICORN_CFLAGS='-ggdb3 -g3 -O0'` for GDB reproduction [issue #437](https://github.com/unicorn-engine/unicorn/issues/437)) and break in `cpu_m68k_get_ccr`, `helper_flush_flags`, and the generated hook helper using lldb on macOS.

   A parallel control in an upstream QEMU m68k build can use `-one-insn-per-tb` (officially documented as useful with `-d` logs) and `-d ...` logging; QEMU documents the former in its [invocation docs](https://www.qemu.org/docs/master/system/invocation.html). For a source build, temporarily enable the already-present commented `tcg_dump_ops()` calls in Unicorn's translator or call it around the m68k TB; compare IR for the one-shot and count-limited TB. QEMU trace events can be built with `./configure --enable-trace-backends=simple` (or `log`); `simple` produces portable binary traces with a Python offline API ([official tracing documentation](https://www.qemu.org/docs/master/devel/tracing.html)). These techniques inspect TCG/state without Python code-hook reads.

7. **A deterministic differential fuzzer is more appropriate than a platform fuzzer.** Make the test input a seedable serialized CPU snapshot plus a bounded byte sequence/window and execution schedule: `{initial D/A/PC/SR, mapped bytes, stop PC, split list/counts, optional hook enable}`. Execute A once for N instructions and B over a schedule whose counts sum to N; after each run canonicalize SR by a non-mutating accessor (after the local fix) and compare PC, D/A, SR, selected memory, and exception/stop reason. On mismatch, retain the input, binary-search the first divergent instruction/split, and delta-debug bytes/schedule. This directly answers one-shot-vs-partitioned behavior and gives deterministic replay/shrinking; AFL++/libFuzzer can mutate that input in a persistent harness, but neither supplies m68k semantics.

   QEMU provides useful patterns, not a ready CPU-semantic harness: its qtest fuzzer calls `LLVMFuzzerTestOneInput` once per input and has pre-fuzz initialization ([`tests/qtest/fuzz/fuzz.c`](https://github.com/qemu/qemu/blob/master/tests/qtest/fuzz/fuzz.c)), while qtest itself is a **device** testing framework ([docs](https://qemu.readthedocs.io/en/v9.2.4/devel/testing/qtest.html)). QEMU has m68k TCG-test build support ([21d71c8](https://github.com/qemu/qemu/commit/21d71c8c414a6c322a2babd5bcf58d3e20ce308c)); add the minimized reproducer as a `tests/tcg/m68k` test if reproducing there. On macOS/arm64, a native C/C++ harness plus Apple clang libFuzzer and ASan/UBSan is still the lowest-friction option. However, AFL++ Unicorn mode does explicitly accept `Darwin` in [`build_unicorn_support.sh`](https://github.com/KastnerRG/fuzz_hw_fuzzing_afl/blob/stable/unicorn_mode/build_unicorn_support.sh), selects `sysctl -n hw.ncpu`, builds UnicornAFL, and validates it through `afl-showmap -U`. Current AFL++ also documents the manual `unicorn_mode/build_unicorn_support.py` build. This establishes Darwin support; a local Apple-silicon build is still needed to verify the pinned UnicornAFL revision and m68k target on this machine.

8. **RISU, qtest, plugins, record/replay: scope distinctions matter.** RISU is traditionally a QEMU-vs-hardware register-state comparator, but I found no primary m68k/ColdFire RISU target evidence; it is not the quickest route without hardware support. QEMU plugins are passive only—official docs say they cannot modify state, but can instrument every instruction/load/store and include `contrib/plugins/execlog` ([plugin docs](https://www.qemu.org/docs/master/devel/tcg-plugins.html)); therefore they can record/replay-comparable traces in a QEMU control run, but not expose TCG temporaries or fix Unicorn. QEMU record/replay is designed around deterministic system-emulation inputs, not a replacement for schedule-differential CPU testing. qtest is unsuitable for this pure CPU translator question except if building a synthetic machine/device fixture.

9. **Ghidra/P-code is useful only as a localized second implementation, with an important warning.** SLEIGH translates instructions into explicit P-code semantics; P-code operations have explicit inputs/outputs and no implicit effects ([SLEIGH documentation](https://github.com/NationalSecurityAgency/ghidra/blob/master/GhidraDocs/languages/html/sleigh.html)). That makes a small emulator script/test around `cmp.l`/branches and saved-SR restoration valuable for differential tests and inspection of X/Z semantics. However, Ghidra PR [#9081](https://github.com/NationalSecurityAgency/ghidra/pull/9081) itself reports nine 68000-family semantic bugs affecting ColdFire, including CMP incorrectly changing X. Treat the exact Ghidra version/spec as a candidate oracle only after checking whether those fixes are present and unit-testing the required subset; it is not a reliable full MCF5441x platform replacement.

10. **Tools to deprioritize.** angr, Manticore, Qiling, PANDA, Avatar2/P2IM/Fuzzware, Renode, and full Ghidra/PyGhidra workflows do not supply a demonstrated MCF5441x/ColdFire V4e full-platform oracle for this narrow lazy-CCR/TB defect. Miasm’s own supported emulation architectures list x86/ARM/MIPS/SH4/MSP430 rather than m68k ([README](https://github.com/cea-sec/miasm/blob/master/README.md)); its Jitter explicitly rejects unlisted architectures ([source](https://github.com/cea-sec/miasm/blob/master/miasm/jitter/jitload.py)). MAME/Musashi might be explored only if a maintained ColdFire V4e core and the exact subset are independently verified; that is an oracle project, not a quick platform migration. None removes the immediate need to identify whether Unicorn's generated hook call or CCR state is stale.

## Ranked recommendations

1. **Quickest decisive experiment — instrument and minimize the existing window.** Keep both local changes (remove SR-read assignment; call `update_cc_op(dc)` before the generated code callback) as separate toggles. Run four configurations: baseline, SR-only, hook-sync-only, both. For each, execute the same restored snapshot (a) uninterrupted, (b) one instruction at a time, and (c) at every split point over a small pre-0x40127c78 window. At the first difference, log the *runtime* six `env->cc_*` fields and `cc_op` immediately after CMP, before the next hook, at TB exit, and on SR read. This distinguishes stale public state, missing CC-op selector synchronization, and corruption of the lazy operands.

2. **Best fuzzing harness — custom persistent C/C++ schedule-differential harness with libFuzzer.** Link directly to the locally patched Unicorn, snapshot/restore with `uc_context_save/restore` or recreate from serialized state, and use `LLVMFuzzerTestOneInput`. The oracle is equality of one-shot and partitioned results, not QEMU. Save every mismatch as a binary seed and provide `--replay seed --split k`; use libFuzzer minimization (`-minimize_crash=1`) after making the mismatch return a deterministic failure. This supports one-shot/partition comparison, replay, shrinking, and macOS/arm64 where the project builds.

3. **Best independent oracle — small P-code/SLEIGH or a separately verified interpreter, not QEMU alone.** Start with CMP/BEQ, then add only instructions in the minimized predecessor slice (including RTE/MOVEM if the minimizer retains them). Verify against the ColdFire reference manual and known vectors. Use QEMU m68k simultaneously as a no-Unicorn-hook and newer-tree control, preferably one-instruction-per-TB; because of shared translator heritage, agreement between QEMU and Unicorn is supportive but not independent proof.

4. **Reject for now — full-platform migration and generic firmware frameworks.** Do not pivot to Renode/Avatar2/P2IM/Fuzzware/PANDA/Qiling or a broad Ghidra/angr/Manticore effort for a failure that already reproduces at CPU state/TB boundaries. They add device/model risk and do not inspect Unicorn’s TCG globals. UnicornAFL is a viable Darwin candidate, but verify its pinned Unicorn revision, m68k build, and Apple-silicon execution locally before adopting it.

## Gaps

I did not find an upstream Unicorn ticket/PR that names the exact continuous-run `cmp.l a2,d4` / `SR=0x2001` case, nor evidence of a post-2.1.4 upstream fix for it. Search results alone cannot prove no unindexed issue exists. The AFL++ Unicorn-mode build scripts establish a Darwin path, but a local build is still required to establish Apple-silicon plus m68k compatibility for the pinned UnicornAFL revision. No primary source established a hardware-validated MCF5441x semantic oracle. The next evidence should be the minimized, non-proprietary instruction/state reproducer and generated-TCG/runtime-state logs; those can support a focused upstream Unicorn report without uploading firmware.
