# QEMU / ColdFire V4m Feasibility — MCF5441x (Digitakt II)

## TL;DR

**Stay on Unicorn.** The two motivating bugs are real, but the evidence does not support "switch to QEMU" as the fix. First, an Unicorn PR (#2161, merged 2025-04-13, already in the 2.1.4 release the project uses) attempted exactly the CCR-merge fix the project needs — but it has a latent ordering bug (it clobbers `env->cc_op` before calling the flag-computation code that switches on it), so `uc_reg_read(UC_M68K_REG_SR)` still returns garbage whenever the last instruction left a lazy (non-`CC_OP_FLAGS`) condition-code state, which is most of the time. The underlying correct-computation machinery (`cpu_m68k_get_ccr`, `helper_flush_flags`) already exists in the same file; the fix is very plausibly a 1–3 line change to `qemu/target/m68k/unicorn.c` in the project's own toolchain. This exact residual bug is independently corroborated by a currently-open upstream issue (#2380, filed by an unrelated reporter in August 2026) with its own matching repro — this is not a hypothesis, it's a live, unfixed, known bug. Second, the two ColdFire-decode bugs the project already worked around (FF1 "not implemented", MOVEC-with-unrecognized-Rc "aborts the process") are **not Unicorn-specific mis-forks** — they are verified, still-present bugs in upstream QEMU's `target/m68k` too (`cfv4e` never sets the ISA feature flag FF1 needs; QEMU's `cf_movec_to` helper only implements 3 control registers and calls a fatal `cpu_abort()` on anything else). Moving to QEMU would not make those problems disappear; you'd be patching the same category of gap in C instead of Python, in a target (ColdFire V4/V4m board support) nobody upstream has ever built or exercised. Third, there is no existing MCF5441x/ColdFire-V4 QEMU machine anywhere (upstream, mailing list, forks, academic, hobbyist) to build on, and QEMU has no eDMA, DMA-timer, or triple-INTC model — a real machine type is a from-scratch, multi-peripheral C project on an architecture with zero precedent. Musashi (MAME's C68k core's ancestor) has **no ColdFire support whatsoever** — not a partial fit, an absent one. Net: patching Unicorn's SR read (shallow, in-tree) and adding a minimal IRQ-assert entry point to Unicorn's m68k target (the CPU-side plumbing for it, `m68k_set_irq_level`/`m68k_cpu_exec_interrupt`, already exists unmodified from QEMU and is simply never called by Unicorn's harness) is the pragmatic path to the stated goal.

## 1. Current upstream QEMU ColdFire support

**VERIFIED** (cloned `github.com/qemu/qemu`, inspected at tag `v11.1.0` and at `master`@`35500e5c41ae` (2026-09-07); QEMU's release cadence has moved past v10.x since this project's knowledge cutoff — v11.0.0 and v11.1.0 both exist).

`hw/m68k/` contents (permalink: https://github.com/qemu/qemu/tree/v11.1.0/hw/m68k):
- `an5206.c` — AN5206 board (MCF5206, ColdFire V2)
- `mcf5206.c` — MCF5206 SoC glue
- `mcf5208.c` — MCF5208EVB board + SoC (MCF5208, ColdFire V2, "ISA A+ with EMAC")
- `mcf_intc.c` — ColdFire interrupt controller model (used by both boards)
- `next-cube.c`, `next-kbd.c` — NeXT Cube (68040-class, unrelated to ColdFire)
- `q800.c`, `q800-glue.c` — Quadra 800 (68040-class, unrelated)
- `virt.c` — generic m68k "virt" board (classic 68k core, not ColdFire)
- `bootinfo.h` — shared boot-info struct

No third ColdFire machine exists. https://www.qemu.org/docs/master/system/target-m68k.html confirms only two ColdFire machines are documented: `an5206` (MCF5206) and `mcf5208evb` (MCF5208), each "Two on-chip UARTs" / "Two on-chip UARTs" respectively (the doc's wording is terse but matches the source: mcf5208.c wires exactly 2 PITs and 3 UARTs, not "three UARTs" as some older mirrors of this doc state — verified against source, see §4).

CPU models (`target/m68k/cpu.c`, permalink https://github.com/qemu/qemu/blob/v11.1.0/target/m68k/cpu.c#L726-L729):
- Classic 680x0: `m68000`, `m68010`, `m68020`, `m68030`, `m68040`, `m68060`
- ColdFire: `m5206` (V2, ISA_A), `m5208` (V2, ISA_A + ISA_A+ + EMAC), `cfv4e` (V4e-labelled, ISA_A + ISA_B + FPU + EMAC), `any` (synthetic superset, ISA_A+B+A+ + FPU + EMAC + EMAC_B — not a real chip)

**`cfv4e` is not "a full V4 implementation" in any sense that matters here — it is an orphaned CPU-core definition with zero board integration and a missing feature flag:**
- No file under `hw/m68k/` references the string `cfv4e` at all (`grep -rn cfv4e hw/m68k/*.c` → zero matches). No machine type instantiates it; it is reachable only by manually overriding `-cpu cfv4e` on the unrelated MCF5208EVB machine (untested combination, no peripherals would match).
- `cfv4e_cpu_initfn` (https://github.com/qemu/qemu/blob/v11.1.0/target/m68k/cpu.c#L349-L360) sets `CF_ISA_A`, `CF_ISA_B`, `BRAL`, `CF_FPU`, `CF_EMAC`, `USP`, `MOVEFROMSR_PRIV` — and does **not** set `CF_ISA_APLUSC`. See §2: this silently disables FF1/BITREV/BYTEREV/STRLDSR decode for the one CPU model that is supposed to represent V4-class ColdFire.
- Real MCF5441x is a "V4m" core per NXP's naming (the "m" suffix conventionally denotes a reduced-complexity variant, no hardware FPU) — `cfv4e` sets `CF_FPU`, which the real chip's core almost certainly lacks. This is **INFERRED** from NXP naming convention, not confirmed against the reference manual's core-description chapter in this pass.

## 2. Completeness of ColdFire instruction support in `target/m68k/`

**VERIFIED**, read directly from `target/m68k/translate.c`, `cpu.c`, `cpu.h`, `helper.c` at v11.1.0.

- **ISA revisions modeled:** `CF_ISA_A`, `CF_ISA_B`, `CF_ISA_APLUSC` exist as feature bits (https://github.com/qemu/qemu/blob/v11.1.0/target/m68k/cpu.h#L505-L509). **There is no `CF_ISA_C` feature anywhere in the tree** (`grep -rn "ISA_C" target/m68k/` → zero hits). The enum comment for `CF_ISA_APLUSC` literally reads "BIT/BITREV, FF1, STRLDSR (ISA A+ or C)" — acknowledging ISA C should also carry these, but no such flag or CPU model exists to express it. QEMU cannot represent an ISA-C ColdFire core at all, only A/A+/B and an ad-hoc "any".
- **MAC/EMAC:** implemented (`gen_mac_*` functions in translate.c, `MACSR_*` flags in helper.c/cpu.h; `CF_EMAC` and `CF_EMAC_B` — dual-accumulate — feature bits exist). `m5208` and `cfv4e` both set `CF_EMAC` only (not `CF_EMAC_B`); only the synthetic `any` sets both.
- **MVZ / MVS:** implemented as a single function `DISAS_INSN(mvzs)` (translate.c:3005) covering both, selected by an opcode bit; registered `INSN(mvzs, 7100, f100, CF_ISA_B)` (translate.c:5908). Present on `cfv4e` (has `CF_ISA_B`).
- **FF1:** implemented (`DISAS_INSN(ff1)`, translate.c:4230, calling `gen_helper_ff1`), but registered as `INSN(ff1, 04c0, fff8, CF_ISA_APLUSC)` (translate.c:5798) — **gated on ISA A+/C, not ISA B**. Since `cfv4e` never sets `CF_ISA_APLUSC` (see §1), **`cfv4e` cannot decode FF1 at all** — it falls through to the illegal-instruction path. Git history: FF1 support was added in commit `821f7e7610` ("Implement ColdFire ff1."), dated **2007-05-28**, and has had no further changes found in this pass (`git log --all --grep=ff1 -- target/m68k` finds only one unrelated hit, an `fmove.l` commit matching the substring "ff1" in an unrelated identifier). It has been essentially untouched for ~19 years. Confirmed directly by re-fetching both init functions at v11.1.0: `m5208_cpu_initfn` (the older, ColdFire **V2** model) *does* call `m68k_set_feature(env, M68K_FEATURE_CF_ISA_APLUSC)` and so decodes FF1 correctly, while `cfv4e_cpu_initfn` sets `CF_ISA_B` and `CF_FPU` instead but omits `CF_ISA_APLUSC` entirely — i.e. QEMU's nominal "V4" ColdFire model is strictly *worse* than its own V2 model on this specific, architecturally-important instruction. This is not a subtle inference; it's visible by diffing the two ~7-line init functions side by side.
- **MOVEC:** implemented as two separate paths — `cf_movec` (ColdFire, `INSN(cf_movec, 4e7b, ffff, CF_ISA_A)`, one-directional register→control-register only, matches real ColdFire MOVEC semantics) and `m68k_movec` (classic 68010+, bidirectional). `cfv4e` has `CF_ISA_A`, so the ColdFire MOVEC *opcode* decodes fine on `cfv4e`. **The bug is downstream, in the helper**: `HELPER(cf_movec_to)` (`target/m68k/helper.c:141`, https://github.com/qemu/qemu/blob/v11.1.0/target/m68k/helper.c#L141-L161) implements exactly three control registers — `CACR`, `ACR0-3` (no-op TODO), `VBR` — and its `default:` case calls `cpu_abort(...)`, a **fatal, non-catchable process abort**, for any other control-register number. This directly and precisely matches the project's own observed symptom (`docs/FINDINGS.md`: "`movec d0,Rc=0x009` … aborts the Unicorn process (SIGABRT)") — `0x009` is not one of the ~5 registers QEMU implements. **This is a genuine, still-open upstream QEMU limitation, confirmed present at v11.1.0/master, not something Unicorn diverged from or that upstream has since fixed.** A commit from 2021-02-01 (`8df0e6aeda`, "MOVEC insn. should generate exception if wrong CR is accessed") only touched the *classic* `m68k_movec` path (restricting it to 68010+); it made no change to `cf_movec`/`cf_movec_to`.
- **TAS:** implemented, `INSN(tas, 4ac0, ffc0, CF_ISA_B)` (translate.c:5856) — present on `cfv4e`.
- **DIVS.L/DIVU.L:** the plain 32/32→32 form (`DISAS_INSN(divl)`, translate.c ~1537, `INSN(divl, 4c40, ffc0, CF_ISA_A)`) is implemented and present on every ColdFire model including `cfv4e`. The **extended 64-bit-dividend, remainder-returning form** (`divX.l <EA>, Dr:Dq`) is gated behind `M68K_FEATURE_QUAD_MULDIV`, which **no ColdFire CPU model sets** (only classic `m68020`+ sets it; `m68060` explicitly unsets it too, "Implemented as a software feature"). If the Digitakt firmware ever uses the extended form, it is unimplemented for any ColdFire target in QEMU.

**Unicorn's m68k target vs. QEMU fork lineage:** Unicorn's `qemu/VERSION` file (https://github.com/unicorn-engine/unicorn/blob/master/qemu/VERSION) reads `5.0.1`, confirming Unicorn 2's m68k target is a fork of QEMU ~5.0.1 (mid-2020). Given FF1 has been essentially unchanged in QEMU since 2007 and `cf_movec_to`'s minimal-register-list-plus-`cpu_abort` behavior is unchanged at least back through that lineage and forward to today's `master`, **both of the ISA-decode bugs the project patched around were already present in QEMU at Unicorn's fork point, and remain present in QEMU today** — this is category (b) from the task's framing ("inherited at fork time and never fixed upstream either"), not category (a) ("QEMU fixed it after the fork"). The one upstream MOVEC-adjacent fix found (`8df0e6aeda`, 2021) is irrelevant to ColdFire because it only touches the classic-68k `m68k_movec` path.

**The CCR/SR bug specifically — and a materially different finding than the task's premise assumed:** Unicorn's own `uc.c`/`target/m68k/unicorn.c` was **not** left with the naive "SR read returns only last-written value" bug forever. PR https://github.com/unicorn-engine/unicorn/pull/2161 ("fix(m68k): correct SR register read", commit `aa86641e`, merged 2025-04-13) changed the read path from:
```c
case UC_M68K_REG_SR:
    *(uint32_t *)value = env->sr;                 // before: literally the bug as described
```
to (current `v2.1.4`, confirmed by direct clone/checkout — this commit **is** an ancestor of the `v2.1.4` tag, i.e. it ships in the exact version the project uses):
```c
case UC_M68K_REG_SR:
    env->cc_op = CC_OP_FLAGS;                      // <-- clobbers the real lazy cc_op first
    *(uint32_t *)value = cpu_m68k_get_sr(env);      // cpu_m68k_get_ccr() then switches on the clobbered cc_op
```
`cpu_m68k_get_ccr()` (`target/m68k/helper.c:822`) computes flags via `COMPUTE_CCR(env->cc_op, ...)`, a macro that switches on `cc_op` to decide how to interpret the raw `cc_n/cc_z/cc_v/cc_c/cc_x` fields (for `CC_OP_ADDB/W/L`, `CC_OP_SUBB/W/L`, `CC_OP_CMPB/W/L`, `CC_OP_LOGIC` these fields hold raw operands/results that must be recombined; only for `CC_OP_FLAGS` are they already final bits). By force-setting `env->cc_op = CC_OP_FLAGS` immediately before this call, the read path always takes the "everything already in place" branch — **regardless of what the real pending op was** — and reinterprets whatever raw operand data is sitting in `cc_n/cc_z/cc_v` as if it were already-materialized flags. The correct pattern already exists two lines above in the same file: `HELPER(flush_flags)` (`helper.c:862`) computes `COMPUTE_CCR(cc_op, ...)` using the **real** cc_op passed in as an argument, and only *then* sets `cc_op = CC_OP_FLAGS`. The shipped fix inlines a broken version of this pattern (sets the tag before doing the work the tag is supposed to describe as already-done). Consequence, mechanistically: any `uc_reg_read(UC_M68K_REG_SR)` taken right after an ADD/SUB/CMP/logic/TST-class instruction (i.e. whenever `cc_op` is not already `CC_OP_FLAGS`, the overwhelmingly common case) returns **wrong flags**, and — because this is a read with a state-mutating side effect — permanently corrupts `env->cc_op` for subsequent real execution too. This is a *precise* mechanistic explanation for the project's own experimental proof (`uc_reg_write(SR, uc_reg_read(SR))` flipping a `tst.l`/`beq` branch): `tst.l` sets `cc_op = CC_OP_LOGIC` (not `CC_OP_FLAGS`); the buggy read computes garbage from that state; the round-trip write then commits the garbage as ground truth via `cpu_m68k_set_ccr`. **This was independently re-derived from source in this pass, not copied from the task's framing — it refines rather than merely confirms the premise.** Not independently rebuilt/re-run against the project's own test case in this pass; the mechanism is verified by direct source reading but the exact reproduction was not re-executed here.

Two related, still-open Unicorn issues corroborate ongoing m68k SR/flag trouble at the 2.0-rc era: https://github.com/unicorn-engine/unicorn/issues/1501 (writing `UC_M68K_REG_SR` silently failed, 2.0.0-rc4, shown closed with no visible resolution in the fetched content) and https://github.com/unicorn-engine/unicorn/issues/1502 (several m68k instructions including `move #$2700,sr` throwing unhandled exceptions, closed with no visible resolution). https://github.com/unicorn-engine/unicorn/issues/1445 separately reports a `cfv4e` addressing-mode-with-instruction-size->2 execution bug, unresolved status not confirmed in this pass — flagged as a secondary risk if pursuing further Unicorn use.

**Confirming independent corroboration (fetched directly, VERIFIED):** issue https://github.com/unicorn-engine/unicorn/issues/2380 — "m68k: reg_read(UC_M68K_REG_SR) silently destroys the guest's condition codes (after any reg_write of SR)" — was opened by a third party (`cwright7101`) on **2026-08-04** (i.e. one month before this research pass, unrelated to this project) and is **still open**. Its own minimal repro is materially the same shape as the project's: write SR, then read it back, and a previously-set condition flag (the reporter uses Z) is silently lost, flipping a subsequent conditional branch (`bne`) — the reporter explicitly attributes it to "QEMU's lazy flag evaluation mechanism" and notes the only workaround is `context_save()`/`context_restore()`. This is exactly the residual post-#2161-fix bug hypothesized from source reading below — it is not a hypothesis needing upstream validation, it is an already-filed, already-open, independently-discovered upstream bug report as of this research date.

Adjacent, non-QEMU prior art worth naming for completeness (not directly useful): MAME (`mamedev/mame`) forked and heavily extended Musashi into its own `src/devices/cpu/m68000/` core with a `CPU_TYPE_COLDFIRE` flag, and merged PR https://github.com/mamedev/mame/pull/13261 (merged 2025-07-13) adding MCF5206E (ColdFire **V2**) SIM/UART/Mbus peripheral device models for the "Pluto 6" gambling-machine emulation. This confirms MAME's core has *some* ColdFire opcode support and that someone has written ColdFire peripheral device models in a C emulator codebase recently — but it is V2-class, tightly coupled to MAME's device/bus infrastructure (not portable to QEMU without a rewrite), and still nowhere near V4/V4m.

## 4. What a new machine type would need

**VERIFIED**, from direct inspection of `hw/m68k/mcf5208.c`, `hw/m68k/mcf_intc.c`, `hw/char/mcf_uart.c`, and `hw/dma/` at v11.1.0, cross-checked against the project's own `docs/refs/MCF5441X-notes.md` (PIT and INTC register tables, sourced from the real MCF5441XRM).

| Peripheral | QEMU today | Verdict |
|---|---|---|
| **PIT0-3** | `hw/m68k/mcf5208.c` defines an inline `m5208_timer_state`/`m5208_timer_*` device (not a separate file), wired as **2 instances** at `0xfc080000`/`0xfc084000`, IRQ lines 4/5 off `mcf_intc`. | **Reusable, bit-exact.** The register layout is an exact match to MCF5441x's real PCSRn (offset 0, 16-bit: `EN`=bit0, `RLD`=bit1, `PIF`=bit2 W1C, `PIE`=bit3, `OVW`=bit4, `DBG`=bit5, `DOZE`=bit6, `PRE[3:0]`=bits11-8), PMRn (offset +2), PCNTRn (offset +4, read-only) — verified field-by-field against `MCF5441X-notes.md §4a` (itself sourced from MCF5441XRM ch. 38). NXP evidently kept this exact PIT IP block across ColdFire V2→V4m. Needed changes: instantiate 4 instead of 2, correct base addresses (4th at `0xfc08c000`), adjust the hardcoded `SYS_FREQ` constant (166,666,666 in mcf5208.c vs. the Digitakt's 132 MHz peripheral bus), and wire to 3 separate INTC instances per source table rather than 1. **Low effort.**
| **INTC0/1/2** | `hw/m68k/mcf_intc.c` (221 lines) is a single-instance model: `uint64_t ipr/imr/ifr` (64-source pending/mask/force registers) + `uint8_t icr[64]` priority array, one `mcf_intc_init()` call per board. MCF5208EVB instantiates exactly **one**. | **Same IP-block generation, wrong cardinality.** MCF5441x's INTC0/1/2 each address 64 sources with `vector = 64 + source` numbering (per `MCF5441X-notes.md §4b`, ch. 17 of the manual) — structurally identical to what `mcf_intc.c` already models. The device *code* is plausibly reusable 3×; the internal register *offsets* within each 0x4000+ block (IPRHn/IPRLn/IMRHn/IMRLn/ICRn exact addresses) were **not** bit-verified against the manual in this pass and would need checking before assuming a drop-in fit. **Low-to-moderate effort**, contingent on that offset check.
| **UART8** | `hw/char/mcf_uart.c` (372 lines), `FIFO_DEPTH=4`, MCF5208EVB wires **3** instances. | Almost certainly the same UART IP block reused across ColdFire generations (Freescale kept this UART largely unchanged for a long time), but this was **not** verified bit-for-bit against MCF5441XRM's UART8 register chapter in this pass — flagged as **INFERRED**, needs a manual cross-check before relying on it. If confirmed, adding an 8th instance is trivial (new base address + IRQ line); if the register set diverged (MCF5441x UARTs may have gained FIFO-depth or extra mode registers vs. the V2-era part), it's a moderate rewrite.
| **eDMA (ch. 35, UART8 TX)** | **Absent entirely.** `hw/dma/` (checked at v11.1.0) contains device models for BCM2835, OMAP, ARM PL080/PL330, RC4030, Sparc32, SiFive, and several Xilinx DMA engines — **no Freescale/NXP eDMA model of any kind**, for any SoC family (ColdFire, Kinetis, i.MX, QorIQ all use variants of the same eDMA IP; none are modeled). `mcf5208.c`'s own header comment explicitly lists `eDMA` among peripherals it does *not* implement. | **From-scratch C device model required.** No prior art anywhere in QEMU to start from.
| **DMA timers DTIM0-3** | **Absent.** Same `mcf5208.c` comment explicitly lists "DMA timers" as unimplemented; no `hw/timer/` file for them was found. | **From-scratch.** Not the same peripheral as the PIT (different register generation per the project's own notes, which found a distinct "HALTED"-named field convention specific to the DMA Timer's DTXMRn register, contrasted against PIT's DBG field) — cannot reuse the PIT work.
| **FlexBus-attached coprocessor** | N/A — project-specific custom hardware, not an NXP-documented peripheral. | Confirmed not present in QEMU (nor could it be; it's bespoke to this product). `mcf5208.c` lists FlexBus itself (the bus, not any device on it) as unimplemented.
| **128×64 OLED over serial** | N/A — project-specific custom hardware. | Confirmed not present in QEMU, unsurprisingly.

Bottom line for §4: of the six real peripherals, one (PIT) is a strong, verified reuse candidate; one (INTC) is a plausible but unverified reuse candidate; one (UART) is a plausible-but-unverified reuse candidate; two (eDMA, DMA timers) require entirely new C device models with zero upstream starting point; and two (FlexBus coprocessor, OLED) were always going to be 100% custom regardless of emulator choice.

## 5. Lighter-weight middle paths

### 5a. `qemu-user` / libqemu-as-a-library

**VERIFIED**, from https://www.qemu.org/docs/master/user/main.html: `qemu-user` (`linux-user` mode, including `qemu-m68k`) exists and supports m68k, but its entire design is "run a Linux userspace ELF binary and translate its syscalls to host equivalents" — it loads an ELF, sets up a Linux-shaped process image, and intercepts `syscall`/trap instructions to redirect to the host kernel. The Digitakt II MAIN OS is a **bare-metal firmware blob** (raw binary loaded at a fixed physical address, no ELF headers, no OS, no syscalls — it *is* the OS) plus a separately-loaded boot stage. There is no "process" for `qemu-user` to set up and no syscall interface for it to intercept; the reasoning in the task background is correct and confirmed by how `qemu-user` actually works, not merely assumed. Not applicable, full stop.

`libqemu` (QEMU packaged as an embeddable library, e.g. via the `qemu-system-*`-as-a-library efforts / QBox / similar) still uses `qemu-system`'s full board-model machinery under the hood — it does not sidestep §3/§4's "no MCF5441x board model exists" problem, it only changes how you host an otherwise-identical `qemu-system-m68k`. It buys nothing here that a normal `qemu-system-m68k -M <new-machine>` doesn't already offer, at the cost of extra embedding complexity.

### 5b. Musashi (`kstenerud/Musashi`)

**VERIFIED**, from direct clone of `github.com/kstenerud/Musashi` (master, commit `313ebf1bd9f`). Musashi has **no ColdFire support of any kind** — not partial, absent:
- `m68k.h`'s `m68k_cpu_type` enum (https://github.com/kstenerud/Musashi/blob/master/m68k.h — line ~96) lists exactly: `M68K_CPU_TYPE_68000`, `68010`, `68EC020`, `68020`, `68EC030`, `68030`, `68EC040`, `68LC040`, `68040`, `SCC68070`. No ColdFire entry exists.
- `readme.txt`: "Musashi is a Motorola 68000, 68010, 68EC020, 68020, 68EC030, 68030, 68EC040 and 68040 emulator" — ColdFire is not mentioned anywhere in the readme or `history.txt`.
- No EMAC/MAC opcodes, no ColdFire-specific FF1/MOVEC/TAS encodings, nothing.
- It does expose a clean, simple IRQ API (`m68k_set_irq(unsigned int int_level)`, or the alternative `m68k_set_virq`/`m68k_get_virq` pair for multi-source wired-OR interrupt lines) — this part of the design is genuinely nicer than anything Unicorn currently exposes. But it's moot: there is no ColdFire core to attach it to.
- Whether its SR/CCR handling would avoid Unicorn's bug is unknowable/inapplicable for the same reason — the question presupposes a ColdFire mode that doesn't exist.

Integrating Musashi "as a drop-in ColdFire core via ctypes" is not a smaller version of the QEMU option — it's a **different, larger project**: someone would have to design and implement ColdFire ISA_A/B/A+ decode, EMAC, and the ColdFire exception model inside Musashi's C interpreter from scratch, with no existing ColdFire code in that codebase to extend (MAME's independently-forked, heavily-modified `m68000` core does have `CPU_TYPE_COLDFIRE`, per §3, but that's a different, MAME-entangled codebase from mainline Musashi, and even that is V2-only).

### 5c. Patching Unicorn itself

**SR read fix — plausibly shallow, source-level fix identified (see §2 for the full mechanism):**
The correct-computation building blocks (`cpu_m68k_get_ccr`, `helper_flush_flags`) already exist unmodified in Unicorn's `qemu/target/m68k/helper.c`. The bug is that `qemu/target/m68k/unicorn.c`'s `UC_M68K_REG_SR` read handler clobbers `env->cc_op = CC_OP_FLAGS` *before* calling code that switches on `cc_op` to decide how to interpret raw flag-state fields, defeating the very purpose of that switch. A plausible fix is on the order of replacing that clobber with a call to the already-correct flush pattern (materialize flags from the **real**, unclobbered `cc_op`, then set `cc_op = CC_OP_FLAGS` — exactly what `helper_flush_flags` already does, just not invoked from this call site). This is a small, self-contained, well-understood change to one file the project already builds/vendors. **Not built or tested in this pass** — this is a source-reading-derived hypothesis about the fix shape, not a verified patch.

**Correction on re-verification:** an open Unicorn GitHub issue describing *this exact* post-fix regression does exist — https://github.com/unicorn-engine/unicorn/issues/2380, opened 2026-08-04 by an unrelated third party, still open as of this research date (see §2 for full detail). So this is not merely a plausible hypothesis derived from reading the source; it is a confirmed, independently-reported, currently-open upstream bug with its own reproduction case, matching the mechanism identified here. (The two older related issues, #1501 and #1502, predate the #2161 fix and describe the pre-fix symptom at the 2.0-rc stage — #2380 is the post-fix one.) This meaningfully de-risks recommendation (c): the project would not be alone in diagnosing or fixing this, and a patch could plausibly be upstreamed against a live issue rather than sitting as a private fork forever.

**IRQ-assertion API — the hard part (a real interrupt controller model) doesn't need building; only a thin entry point does:** Unicorn's `target/m68k/cpu.c` (inherited unmodified from QEMU) already contains `void m68k_set_irq_level(M68kCPU *cpu, int level, uint8_t vector)` and registers `cc->cpu_exec_interrupt = m68k_cpu_exec_interrupt` — i.e., the CPU-level mechanism for accepting an externally-asserted interrupt level+vector and taking the exception is present and untouched from real QEMU; it's simply never called by anything in Unicorn's harness (Unicorn strips out the `hw/`-level board/qdev/irq-line code that would normally call it from a peripheral model). Exposing it would mean adding one new `uc_m68k_*` public API entry point that calls the existing `m68k_set_irq_level()`, plus confirming Unicorn's generic (shared-across-architectures) interrupt-check-before-next-TB loop actually dispatches through `cpu_exec_interrupt` for m68k the same way it does for other targets (very likely already true, since it's shared infrastructure). For comparison, ARM — a much higher-profile Unicorn target — still has **no** public NVIC/IRQ-injection API years after repeated requests (https://github.com/unicorn-engine/unicorn/issues/825, /issues/591; per a corroborating GitHub discussion, users have had to hand-roll their own NVIC modeling outside Unicorn). That lack of precedent elsewhere is itself informative — Unicorn's maintainers have not prioritized this feature class for any architecture — but the m68k-specific plumbing already existing at the CPU level (unlike, evidently, some other targets) suggests the *m68k* case specifically is closer to "expose an existing internal function" than "design and add a new interrupt-controller subsystem."

## 6. Bottom line recommendation

Effort estimates (engineer-days, single experienced engineer, order-of-magnitude, not a committed plan):

- **(a) New QEMU machine type for MCF5441x from scratch:** roughly **20–40+ days**. No prior art (§3) to shrink this. Breakdown: PIT reuse-with-adaptation (~1-2d, high confidence per the bit-exact match), INTC ×3 (~3-5d, needs offset verification first), UART ×8 (~3-5d, needs register verification first), eDMA channel model sufficient for one TX channel (~5-10d, from scratch, no prior art, DMA engines are fiddly to get right even minimally), DMA timers (~3-5d, from scratch), FlexBus coprocessor + OLED-over-serial stub models (~3-5d, project already understands this hardware from the Unicorn side so mostly porting logic, not discovering it), plus board wiring, boot-image loading to match the project's existing `0x40000400` load convention, and — separately and non-trivially — **fixing the two verified upstream QEMU ColdFire bugs found in §2** (`cfv4e`'s missing `CF_ISA_APLUSC`, one-line but you have to find it; `cf_movec_to`'s minimal control-register list, need to identify what MCF5441x's actual extra control registers are and extend the switch, non-trivial without the same manual research already done for peripherals) before the CPU core is even usable for this firmware. Then there's the fact that nobody has ever booted ColdFire V4-class firmware under QEMU, so expect the *unknown* bugs beyond the two already found.
- **(b) Musashi via ctypes/cffi as a drop-in core replacement:** not a smaller version of (a) — arguably **larger**, because it requires originating ColdFire ISA support in a codebase that has never had any, with no reference implementation inside that codebase to crib from (MAME's fork is a different, entangled codebase). Rough estimate **25-45+ days** just for correct-enough ColdFire decode+EMAC+exception-model in Musashi, before any peripheral work. Not recommended.
- **(c) Patching Unicorn (SR fix + minimal IRQ API):** **2-5 days** for the SR fix (small, localized, source-level fix hypothesis already identified in §5c; budget includes writing a focused regression test mirroring the project's own `tst.l`/`beq` experiment, and rebuilding/vendoring the patched Unicorn) plus **3-7 days** for a minimal `uc_m68k_set_irq(level, vector)`-style API (the CPU-side mechanism already exists per §5c; effort is mostly in the Unicorn-API/binding plumbing, testing that the generic interrupt-check loop actually fires it, and validating exception-frame push/`rte` behavior end-to-end against what the project's existing hand-rolled frame synthesis currently does). Total **5-12 days**, in the project's existing toolchain, no new build target, no new peripheral models needed (all current hand-modelled Python peripherals keep working unchanged).

**Recommendation: pursue (c).** The stated goal is getting this specific firmware's UI booting, not building general-purpose ColdFire V4 QEMU support for its own sake. QEMU does not offer a shortcut here — its ColdFire target has the *same* category of unimplemented/wrong-instruction bugs the project already found and hand-patched in Unicorn (§2), it has zero board-level prior art for this chip family (§3), and it's missing several peripherals outright that would need writing from scratch regardless of which emulator hosts them (§4) — so switching emulators would trade a working, already-debugged Python peripheral layer for months of rebuilding the same peripheral layer in C on a less-travelled target, in a project that has never had ColdFire V4 firmware run under it by anyone, ever. Meanwhile the two hard architectural complaints against Unicorn (stale CCR on synthesized exception frames, no IRQ-assert API) both turn out, on direct source inspection, to have plausible small fixes reachable without leaving Unicorn at all: the flag-computation code the SR read needs already exists in the same file and is used correctly two lines away by another function; the CPU-level interrupt-acceptance code the IRQ API needs already exists unmodified from QEMU and is simply never invoked. "Stay on Unicorn, patch it precisely" is not a consolation-prize conclusion here — it is the option best supported by what's actually in the source trees.
